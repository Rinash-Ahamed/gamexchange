# GameXchange production-readiness audit

Date: 5 November 2026. Scope adapted from the requested Ayursarga audit to GameXchange with the owner's confirmation. This is a source/configuration, dependency and isolated local test audit, not a production penetration test or a certified load-capacity assessment.

## Launch decision

**Do not launch real-money ecommerce on this revision.** The code intentionally accepts only Razorpay test keys and does not reserve/decrement inventory, calculate shipping/serviceability, implement refunds or provide customer order-history/recovery. Keep that guard intact until those business workflows are designed and verified. A public informational/enquiry storefront has a narrower release scope, but deployed rules/IAM, production configuration, images, authentication and monitoring still require owner verification.

No hosting migration, CPU upgrade, automatic deployment, remote Firebase changes, production load generation, payment, email delivery or customer-data mutation was performed. No .env.local contents or customer records were inspected. Existing unrelated worktree changes were preserved. Vercel account telemetry/billing, Firebase console rules/index settings/backups and isolated provider credentials/test users were not available as evidence.

## Architecture and request inventory

- Next.js 16.4.3 App Router, React 19.3.1, strict TypeScript, Tailwind 4, Motion, Zod; Node 24.x pinned. Firebase browser SDK is used for authentication only. Server-only Firebase Admin SDK accesses Firestore and Storage. Razorpay uses bounded server REST calls; Gmail uses backend Nodemailer.
- At inspection: 26 page source files, 14 API route files and roughly 223 source files before audit additions. Static policy/contact/enquiry pages coexist with dynamic homepage/shop/cart/franchise/managed admin routes.
- Public data: cached 60-second product/banner/FAQ/homepage/franchise reads and explicit mutation invalidation. Homepage starts optional content reads concurrently and streams sections behind Suspense, without a homepage inventory read. Optional-section failure does not replace stock with fabricated products.
- Storefront: all public products are delivered for local filters/search; 20-card client pagination bounds DOM work only. Detail metadata/page reads share request-scoped cache but obtain the whole public catalogue. There is no browser Firestore subscription or per-keystroke database query.
- Private boundary: server-verified Google customer identity and order ownership for checkout; approved UID, verified email, current MFA enrollment, TOTP claim, revocation/account checks, secure HTTP-only same-site cookie and 15-minute server idle limit for administrators. This is one business with full-access approved admins, not hospital/consultant tenancy. No other consumer's order-details API exists.
- APIs: enquiry token/submission; admin session/activity/readiness; test order creation/verification/webhook; four managed-image families; liveness; scheduler email worker. Admin mutations also use server actions. Public repair/gaming/trade/franchise forms return WhatsApp drafts, not durable bookings.

Failure domains: Firebase is shared by accounts, private data, uploaded artwork and distributed abuse protection, so its outage can affect several flows at once. Razorpay is the sole checkout provider; Gmail is the sole transactional mail transport. Durable order/job records separate mail failure from payment verification, but there is no alternate provider/region failover demonstrated. Per-instance byte caches are performance aids, not durable replicas. Optional homepage sections can degrade independently; shop failure must not be mistaken for empty real inventory. Sharp encoding is bounded and restricted to authenticated uploads but still consumes native CPU/memory; actual image cold-optimization, function budgets and provider timeouts need region-specific measurement rather than a CPU upgrade assumption.

## Firestore query, index and cost review

| Area | Query shape and expected cost | Scaling/index notes |
| --- | --- | --- |
| Public products | status in active/out-of-stock + category registry read; full N docs on cache miss | Single-field index sufficient by query shape, subject to actual deployed index settings. Cache reduces frequency, not miss cost or full response payload. Cold/warm multi-instance behavior needs measurement. |
| Product detail | Same cached full catalogue, in-memory lookup/related sorting | Avoid N-sized query/DTO to serve one ID at scale; retain public visibility boundary and accurate related semantics in redesign. |
| Images | One current metadata read per image origin request, followed by bounded/coalesced Storage bytes | Browser/Next optimizer caching helps public immutable artwork; authorization/visibility is not cached. Four caches allow up to roughly 32 MiB stored bytes combined, excluding in-flight buffers/Sharp/browser images. |
| Admin lists | Inventory orderBy updatedAt full list; services orderBy createdAt full list | Cursor pagination with deterministic tie-breaker; do not use offsets. Dashboard uses four aggregates plus latest five services rather than loading all to count. |
| Categories/settings | Up to 100 categories in one doc; delete checks all inventory, including legacy aliases | Referential safety intentionally transactional. Plan reference counts/legacy migration before removing whole-collection checks. FAQ/banner/franchise caps bound their normal sizes. |
| Orders/history | Latest 50 orders; managing one selected order queries at most three email jobs, not N+1 across 50 | Older orders have no pagination/search UI. Add cursors/history lookup when operational volume needs them; do not silently lose access after 50. |
| Email worker | nextAttemptAt inequality, limit 5; claim/result transactions per job | Single-field index sufficient by shape. No listener. Monitor pending age and uncertain jobs, not just scheduler HTTP success. |
| Protection/session | Per-key shared rate transactions, atomic nonce creation, hashed-cookie idle reads/touches | At least a read/write for each allowed rate window operation plus contention retries; guard amplification needs measured traffic and quotas. Five-second caller timeouts cannot cancel submitted Firestore work. |
| Audit log | New random doc per audited inventory/category/service mutation; latest 50 reads | Append-only in app, not tamper-proof against service-account/project-owner compromise. No full audit coverage of homepage/provider changes. |

There is no onSnapshot or client database listener in current source. No composite-index dependency was identified in current query shapes; actual disabled single-field indexes/region settings were not inspected. UUID/HMAC-based IDs avoid sequential document IDs, but indexed timestamps and shared documents still need write-load review. Exempt large unqueried descriptions/maps/address/item/history fields and temporary TTL fields from indexing only after confirming all queries; no remote index change was made. [Firestore best practices](https://firebase.google.com/docs/firestore/best-practices), [index overview](https://firebase.google.com/docs/firestore/query-data/index-overview).

## Checkout, order and email reliability

Verified in source: owner-bound request UUID/fingerprint; server price/stock snapshot; integer paise; signature checks; fetched gateway payment matching order/amount/currency/captured/no refunds; paid state changed transactionally; repeated same-payment callback is a no-op. Atomic paid/history/email job creation is never triggered by a success page. Parcel Sent requires the next status and creates one deterministic shipment job in that transaction. Concurrent job claims use a token/lease; definite failures have bounded backoff; uncertain sends stop rather than duplicate. Customer/business mailbox comparisons normalize case/whitespace and Gmail aliases. SMTP sends after the response and does not roll back paid orders.

Limits: uncertain gateway creation stays creating for manual reconciliation; browser verification recovery is memory-only; no consumer order-history endpoint; no real-stock reservation or refund lifecycle. Gmail SMTP does not offer exactly-once delivery. The queue avoids blind retries, but uncertain sends need mailbox review. A crashed worker must be revisited by the scheduler to mark an expired lease uncertain. A manually created service ticket uses a generated ID and is not a retry-idempotent consumer booking. Source review and pure-policy tests do not prove actual concurrent Firestore/provider behavior.

## Production monitoring and operational release checklist

1. In the correct Vercel project/environment, review deployment Node version, region, runtime 5xx/timeout logs, cold versus warm execution, request volume, outbound latency, memory/CPU/throttling and image optimization traffic. No screenshot or old Ready deployment status proves runtime health. Export an aligned staging test window before proposing compute changes. [Runtime Logs](https://vercel.com/docs/logs/runtime), [Observability](https://vercel.com/docs/observability).
2. Use the new request_result, unhandled_request_error, email_queue_unavailable and email_queue_processing_failed events for alerts. Do not log bearer tokens, cookies, request bodies, provider exceptions, customer email/phone/address or payment signatures. Our hooks omit them; review hosting/framework/provider logs and access/retention separately, because a custom hook cannot redact every platform log automatically.
3. Liveness /api/health is anonymous and inexpensive. /api/admin/readiness stays protected/no-store and is a read-only dependency probe, not proof of writes, payments, backups or SMTP. Add trusted alert delivery without publishing the admin session or weakening this boundary.
4. Configure the requested 30-minute retry schedule, monitor last successful run, oldest due job and uncertain count, and alert after missed runs. Current code has no remote schedule. Vercel Hobby does not support a 30-minute cron, so verify your existing plan or use an approved trusted scheduler; this is not a reason to automatically upgrade CPU or migrate hosting. [Cron usage/limits](https://vercel.com/docs/cron-jobs/usage-and-pricing).
5. Enable separate Firebase/Google Cloud and Vercel budget alerts at agreed percentages plus daily anomaly alerts. Alerts-only budgets do not automatically cap spending; understand the selected platform's controls before enabling an emergency pause that could interrupt payments. Review usage by project/environment and avoid granting broad owner permissions to the runtime service account. [Google Cloud budget guidance](https://docs.cloud.google.com/billing/docs/how-to/budgets).
6. Verify Firestore scheduled backups/PITR and Storage recovery/retention options, document business-approved RPO/RTO and rehearse a restore into an isolated project. Restore records and referenced image versions together. Never delete suspected orphan images without cross-checking every saved reference and retention/recovery needs. [Firestore disaster recovery](https://firebase.google.com/docs/firestore/disaster-recovery).
7. Rollback: retain the previous verified Vercel deployment and commit/package lock; roll application code back without deleting business records. Do not roll back to code lacking ownership/MFA/idempotency guards. Reconcile provider payments/uncertain jobs before retries and pause acceptance if order state cannot be trusted. Define credential rotation, incident contact and reconciliation responsibilities.
8. Complete legal/business review of privacy, delivery/refund/tax promises and communication retention. Confirm the business sender account/App Password and that test notifications cannot be mistaken for shipments. Never send marketing through transactional consent.

Firestore server libraries bypass Security Rules and use IAM; review both controls independently. [Firebase security boundary](https://firebase.google.com/docs/firestore/security/rules-conditions).

## Staging acceptance required before real commerce

- Two distinct Google consumers: ownership mismatch, token revocation/expiry, unknown/disabled provider and mobile popup handling; no shared bearer fixture.
- Admin: denied non-allowlisted/non-TOTP/unverified users, revoked/deleted/disabled account, idle boundary/cross-tab/sleep/offline and all mutating actions.
- Transaction contention: duplicate order create/callback/webhook concurrently, changed cart prices, two consumers buying final stock after reservation is implemented, lost commit acknowledgement and service/editor conflicts.
- Uploads: rejection of bad MIME/decode/animation/dimensions/byte limits, replacement/removal/reorder, storage absence and commit-then-network-timeout faults with no referenced object deletion.
- Notifications: configured/unconfigured/rejected SMTP, accepted-then-disconnected outcome, post-send Firestore failure, worker interruption, scheduler overlap, same mailbox aliases and exactly one shipment job. Check both Gmail rendering and actual receipt, not only sendMail resolution.
- Recovery: browser refresh after payment, missing callback delivered by webhook, refund/cancel reconciliation, queue backlog, image restore, rollback and budget alert exercises.
- Isolated load profiles 10/50/100/500/1000 with p50/p95/p99, errors, throughput, aligned CPU/memory/throttling and Firestore operation counts. Scripts and guarded instructions are in LOAD_TESTING.md; no profile has been run.
