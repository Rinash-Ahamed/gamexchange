# Checkout stock reservations

Implemented on 5 November 2026. This is an isolated TEST-mode implementation, not live commerce activation. Public inventory, prices, images and availability counts are not mutated. Live Razorpay keys are still rejected. Existing unrelated pagination work is preserved.

## Reservation and payment rules

- Checkout uses a Firestore transaction to read current inventory/prices, read all shared sandbox stock counters, check the whole cart and create its order plus holds atomically. Concurrent last-unit requests contend on the same stock document. A failed multi-item reservation commits nothing and never opens a gateway order.
- `checkoutTestStock` counters are scoped by a hash of the test key ID and product ID. Capacity is seeded once from the current inventory quantity; held and sold units consume that capacity. Sold test units stay sold. Admin restocks do not reset this ledger automatically. This prevents test callbacks from subtracting actual sellable stock. Test-ledger reset/restock tooling is not implemented: reconcile every associated pending payment before any manual maintenance. Never delete a ledger with held or sold orders to bypass the limit.
- Ten-minute holds start at server order creation. Reusing the request UUID does not renew the timer, reserve twice or create another gateway order. Changed customer/cart/delivery/consent details cannot reuse the UUID. The checkout modal uses the remaining timeout as a usability aid, not a security boundary. Expired checkout attempts cannot reopen through the order API; refresh the cart for a new attempt only if no payment is pending.
- Payment success still requires server-side callback HMAC validation and verified customer ownership, or an authenticated webhook, followed by a server Razorpay payment fetch. Order association, amount, INR currency, captured status and an explicitly supplied zero refunded amount must match. Browser success and authorization alone are insufficient.
- Confirmation atomically consumes the order's hold, marks it paid, claims the payment ID permanently in `checkoutTestPayments`, and creates the two deterministic email jobs. Callback/webhook retries cannot consume twice, claim the same payment for another order, duplicate history or queue extra success emails. Gateway calls and emails are outside transaction retries.
- Historical already-paid orders remain idempotent without retroactive stock deduction. Previously unpaid orders without a reservation go to payment review if captured: no invented historic reservation, confirmation or fulfilment.

## Expiry and delayed payments

`GET /api/internal/checkout-reservations` is a server-only scheduler endpoint protected with `Authorization: Bearer <CRON_SECRET>` using the same independent secret as the email worker. It has no public browser release/cancel endpoint.

Configure a trusted scheduler to call this endpoint every minute, separately from the email worker's existing 30-minute schedule. No scheduler, hosting plan, cron deployment configuration, Firebase data or provider settings were changed by this implementation. Until configured, unpaid holds are not automatically released. Do not claim an operational ten-minute release merely because the endpoint builds. Retention TTL must not delete order, stock, payment-claim or email records.

Each invocation processes at most five due orders concurrently. The due query uses `reservationCheckAt` with a matching ascending order and limit; it does not scan all orders or require a compound application query. Verify that field's index is enabled on staging. Five checks per minute is a bounded recovery capacity, not a scalability guarantee; alert on backlog and review before raising the batch. Slow provider calls cannot block a public checkout request.

Before releasing an expired hold, the worker fetches the gateway order and its payments. Captured payments are verified/committed instead of released. Only a matching unpaid created/attempted order with a complete payment list containing no pending/authorized/refunded/unknown attempts is released. Known failed attempts or an empty payment list qualify. Uncertain creation without a saved gateway ID, key changes, provider outages and ambiguous payment states retain the hold, record a safe admin note and defer checking. A failed browser payment or closed tab alone never frees stock.

A status check is a snapshot, not cancellation of future gateway attempts. If payment captures after release, the same atomic confirmation transaction can consume still-free test capacity only if the entire cart fits. Otherwise it records `payment_review` with payment ID and a review note, returns a do-not-pay-again message to the customer, and acknowledges signed webhook reconciliation without approving fulfilment or sending success emails. Admin > Test orders exposes this condition and does not offer fulfilment actions. Manual gateway reconciliation/refund is required; automatic refunds and review-resolution controls are not implemented. This prevents duplicate stock allocation, but cannot promise that a very late payment will never require a refund.

Never release an uncertain hold merely to clear the backlog. Reconcile the gateway receipt/payment first. No real shipping should be performed for these test records.

## Verification and launch gates

- Source and whitespace review only for this update. Build, lint, type checks and tests have not been run because they require an explicit request under AGENTS.md.
- Added `tests/e2e/payment-stock.spec.ts` and an isolated in-memory harness loading the actual payment/reservation modules. Cases cover competing last-unit requests, duplicate creates/callbacks/webhooks, wrong signatures/customer/amount/currency/refund state, authorized-only payments, reconciled expiry, outages/uncertain creation, captured recovery and late multi-item capture. The fake database serializes transactions, enforces reads before writes and models rollback. These tests are not proof of actual Firestore locking or provider delivery and are not yet executed. The automatic postbuild fixture health gate also includes unauthorized reservation-worker rejection, not run in this update.
- Required staging checks: real Firestore transaction contention, same-key creation races, expiry versus capture races, duplicate/reordered signed webhooks, provider outages/ambiguous creation, scheduler authorization/backlog, admin review visibility, browser dismissal/refresh/mobile and email queue behavior. Use test keys and sample addresses only. No live Firebase/payment/email/provider calls or deployment were performed.
- Before live payments: explicitly authorize and implement real inventory reservation/decrement with admin stock editing and public cache invalidation; choose operational late-payment/refund/reconciliation handling; verify the full provider-backed race tests, monitoring and scheduler. The current isolated ledger does not protect real purchases because real purchases are not enabled.
